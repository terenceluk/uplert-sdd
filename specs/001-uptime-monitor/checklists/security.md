## Session Handling

- [ ] CHK008 Are session cookie security attributes (HttpOnly, SameSite, Secure) stated as a requirement anywhere in spec.md/plan.md, or do they exist only as an implementation note in research.md with no spec-level backing? [Traceability, Research §4]
- [ ] CHK009 Is a decision on the `Secure` cookie flag documented given the app must also run over plain HTTP on localhost (Constitution Principle I), where `Secure` cookies would not be sent? [Gap, Conflict-check, Research §4]
- [ ] CHK010 Is session token lifetime/expiration defined, or is indefinite session validity until explicit logout (Data-Model §Session: "no expiry sweep") a reviewed and accepted decision rather than an unexamined gap? [Assumption, Data-Model §Session]
- [ ] CHK011 Are requirements defined for behavior with multiple concurrent sessions for the same user (e.g., several browsers signed in at once)? [Gap, Coverage]
- [ ] CHK012 Is the interaction between a cascading user-delete and an in-flight request authenticated by that user's now-deleted session specified, or left as an unaddressed edge case? [Edge Case, Data-Model §Session]
- [ ] CHK013 Are requirements defined for keeping the session token out of logs, URLs, and error messages, consistent with the password-logging prohibition in the constitution? [Gap, Consistency, Constitution Principle V]

## Input Validation

- [ ] CHK019 Are the rules for "a syntactically valid http(s) URL" (FR-005) specific enough to be objectively, consistently testable, or left open to implementer interpretation? [Measurability, Spec §FR-005]
- [x] CHK020 Are maximum-length requirements defined for `url`, `displayName`, `login`, and `password`, or is unbounded input length an unaddressed gap? [Gap, Completeness] — Resolved 2026-10-17: FR-001 (login 254, password 1024) and FR-005 (url 2048, displayName 100), enforced in data-model.md's schema and contracts/api.md's 400 cases.
- [ ] CHK021 Does the "syntactically valid http(s) URL" requirement address URLs with embedded credentials (`http://user:pass@host/`) or non-http(s) look-alike schemes, or leave that case ambiguous? [Ambiguity, Spec §FR-005]
- [ ] CHK022 Are the boundary values for `intervalSeconds` (exactly 60, exactly 86400) explicitly required to be inclusive, or is boundary behavior only implied by prose ("between 1 minute and 24 hours")? [Clarity, Spec §FR-004, FR-005, Data-Model §Check]
- [ ] CHK023 Are validation requirements for registration/login inputs defined for malformed or oversized payloads, distinct from the basic non-empty check in FR-001? [Gap, Spec §FR-001]
- [ ] CHK024 Is there a requirement describing whether a validation-error response may safely echo back the rejected input value, or is that left unspecified? [Gap]

## Poller Requests to User-Supplied URLs

- [ ] CHK025 Are requirements defined for whether the poller follows HTTP redirects from a monitored URL, and if so, whether a redirect target is re-validated against the same URL rules as the original? [Gap, Spec §FR-006a]
- [x] CHK026 Are requirements defined for whether the poller may reach private/internal network destinations (RFC 1918 ranges, `localhost`, link-local addresses) given it accepts an arbitrary user-supplied URL? [Gap, Spec §FR-006a] — Resolved 2026-10-17: FR-019 requires blocking these destinations.
- [x] CHK027 Is there a documented decision on exposure to cloud-metadata-style endpoints (e.g., `169.254.169.254`) reachable from a user-supplied URL? [Gap, Spec §FR-006a] — Resolved 2026-10-17: FR-019 explicitly names metadata addresses as blocked.
- [ ] CHK028 Are requirements defined for a maximum response size the poller will read before classifying a poll, bounding resource use from a large or unbounded response body? [Gap]
- [x] CHK029 Does the 10-second timeout requirement (Spec §Clarifications, FR-008) specify whether it covers the whole request (connect + transfer) or only time-to-first-byte, and is that distinction material to classification consistency? [Clarity, Spec §Clarifications] — Resolved 2026-10-17: FR-008 now specifies the 10 seconds covers the whole request (connect through fully reading the response), not time-to-first-byte; propagated to data-model.md, research.md §6, and tasks.md T018/T026.
- [ ] CHK030 Are requirements defined for a user-supplied URL whose DNS resolution changes between polls (e.g., resolving to a different or internal address), or is that scenario unaddressed? [Gap, Edge Case] — Note: FR-019's per-poll re-check (added 2026-10-17) substantially addresses this; left for reviewer to confirm and check off, since it was not one of the items explicitly named for resolution in this session.
- [ ] CHK031 Is there a requirement bounding how many checks (and therefore concurrent outbound polls) a single user, or the system overall, may have in flight at once? [Gap, Plan §Constraints]
- [ ] CHK032 Does the "status code, or an equivalent failure indicator" requirement (FR-007) distinguish DNS failure, connection refusal, and timeout, or treat all three uniformly as "down" without further requirement detail? [Clarity, Spec §FR-007, FR-008]
